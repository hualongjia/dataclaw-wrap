# 管理端导航权限查询设计

## Context

`router/index.ts` 的会话检查已经支持复用已加载的权限。随后执行的 `ensureInitStatus()` 再次调用 `loadPermissions()`，而角色管理资格查询又发生在判断目标路由的 `roleManagement` 标记之前。两处调用共同形成了提案中测到的串行等待。现有侧栏按权限码过滤普通菜单，按 `canManageRoles` 过滤角色权限入口。

## Goals / Non-Goals

本次调整浏览器发起查询的时机和前端状态的作用域。页面数据请求、服务端每次管理读写的授权判断、Auth3 接口选型和 CSRF 初始化各自沿用现有流程。角色权限页面内的角色列表、权限树、绑定和编辑数据继续按现有页面流程加载。

## Decisions

1. **普通导航读取内存快照。** 会话验证成功后取得权限，路由继续检查后台准入、目标权限码和租户初始化状态。移除初始化状态查询中附带的重复权限加载；租户初始化成功并影响权限时，在完成事件主动失效快照。两个并行消费者共用当前范围内的一次请求。只把两个接口并行化仍会让普通导航等待较慢的一项。
2. **侧栏显示与角色页准入分别触发。** 同一身份初次显示后台布局时异步取资格；直到得到肯定结果才显示菜单。进入受保护角色路由时重新核验，包括直达及旧地址。两者相遇可共享同一范围仍在途的查询；若直达页面已完成核验，随后挂载的侧栏可直接读取其结果。每次进入角色页均须取得本次核验结果。服务端负责实际操作授权。
3. **把并发响应绑定到身份和刷新批次。** 复用已有权限状态，登记已验证的用户、租户和页面会话。登出、401、重登和切换租户时清理权限、资格及在途请求引用。在成功或失败回写前核对批次；撤权或刷新前启动的旧请求也不能覆盖新结果。首次权限加载失败时保留可重试状态，禁止按旧快照进入受保护页面。
4. **在事件发生处刷新。** 保存可能影响本人的授权后复核权限和相关资格；若保存响应无法判断影响范围，可在这类授权保存成功后保守复核一次。对业务访问被拒的反馈，同时覆盖普通 API 客户端和角色管理的独立 fetch 路径。管理操作被拒时先收起相关数据，再复核；区分会话失效、CSRF 来源错误和业务权限拒绝。合并同时发生的复核，排除复核请求自身，保留原操作的错误结果。
5. **以实际请求数验收。** 在权限已加载且没有失效事件时，任意普通菜单切换均无需发出两个导航权限请求。页面懒加载和业务请求仍可能耗时，305–841 毫秒仅是改动前六次采样中两项请求的合计。

## Risks / Trade-offs

- 其他管理员从外部授予权限后，用户可能在刷新页面或下一次失效事件后才看到入口。用户已接受这一取舍，因此无需为权限设置 30 秒过期时间。
- 已在其他会话撤销的权限可能短暂保留在菜单上。服务端独立鉴权，前端在收到权限拒绝时复核并更新可见内容。
- 现有规范描述本应用系统管理员角色，当前后端资格接口还校验 Auth3 应用管理员关系。前端统一消费服务端资格结论，本次不重新定义管理员身份或改变服务端授权策略。

## Migration Plan

随管理端前端发布，以 Chrome 的普通菜单请求计数和角色页直达行为验收。回滚可重新部署原前端构建，无数据迁移。
