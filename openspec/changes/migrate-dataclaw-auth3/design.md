# Design

## Context

AuthController 已有三条换票路由，共用 AuthService。两个浏览器前端各有运行时回调路由。ModelApiService 自行验票并维护本地应用配额。现有 access-matrix 提供只读展示，权限声明与守卫可复用。参考 p3demo 的应用角色管理、滑动会话和目录同步行为，适配现有 DataClaw 调用方。

## Goals / Non-Goals

最小化业务变化。用户和租户 ID 在 Auth2、Auth3 中一致，跨 JSON 边界保留十进制字符串精度。工作区和模型服务沿用现有本地标识。完整组织树、外部 Client 白名单、Auth3 Client 到模型应用的映射、KMS 独立应用迁移均在本期范围之外。

## Decisions

1. 每个登录事务记录目标端、一次性 state、verifier 和返回地址。管理端建议使用 /auth/admin/callback，用户端使用 /auth/web/callback，桌面沿用 dataclaw://auth/callback。桌面统一通过系统浏览器进行 OAuth 登录，移除账号密码表单、preload/IPC 密码入口和旧密码协议调用，不增加密码代登机器凭证。分别调用现有 /api/v1/{admin,web,desktop}/auth/token，服务端按目标选择 Client，以完全匹配的 redirect_uri 调用 Auth3 /oauth/token。隔离两端浏览器会话，处理失败、登出及切租户后缓存失效；采用滑动策略时允许省略 refresh_token，以 Auth3 租约验证为准，参照 p3demo 区分用户活动与后台轮询。
2. 封装服务端机器凭证获取及过期更新。模型 API 用机器令牌调用 /api/v3/oauth/introspect 并验证用户主体；其余 AppKey、供应商、用户密钥和 quotaContext 逻辑沿用。对其他用户接口按调用端校验身份和应用权限，避免把模型 API 的外部令牌规则扩展到后台管理。
3. 保留前端已有用户查询契约，在适配层转换 Auth3 的本人资料、授权租户、用户分页与批量人员查询结果。记忆管理用机器令牌和来自验证上下文的 X-Tenant-Id 调用 GET /api/v3/orgs/tree（org.tree），直接取 data 顶层 orgId，保留孤立父节点语义。定时消息对照现有 AuthMessageService 的收件人、渠道、附件、失败反馈逐项适配。
4. 管理写操作调用 /api/v3/app/*，令牌归属固定为 dataclaw-admin，成员受其当前租户约束。角色管理采用统一资格查询：服务端从已验证用户身份取得角色 ID，按部署时在管理应用角色目录中核实的系统管理员角色 ID 与编码匹配。前端依据资格结果显示菜单、开放路由和操作按钮。角色、权限码、绑定及成员的每次管理读写均在服务端重新校验同一资格，替换这些入口原有的逐动作权限码门槛。同步、审计等业务入口继续按各自权限码授权。角色权限矩阵保存完整绑定，成员跨页增删提交差量；应用管理员资格与本地同步权限分别检查。
5. 参考 p3demo 全局目标配置、执行历史及逐租户结果模型。通过数据库唯一约束控制有效目标和目录业务键（租户、租户内用户）。每次执行快照化目标；分页完整后在单目标事务内幂等更新镜像并调和失效记录。机器授权收窄或分页失败时保留旧快照。调度采用可续租锁与数据库执行代次，过期持有者无法提交；定时任务按时间槽去重，接管时记录中断。默认调度间隔建议沿用参考项目的 30 分钟。

### 两个浏览器端的独立会话

浏览器 OAuth 回调完成换票后，服务端生成随机会话 ID，在共享 Redis 中记录目标端、已验证的用户和租户以及 Auth3 令牌。响应只下发带签名的 HttpOnly 会话 Cookie。两端分别读取自己的 Cookie 并验证签名及记录所属端。前端通过会话查询获取显示所需的身份，移除从 Cookie 读取令牌及拼装 Bearer 头的逻辑。服务端从已验证会话取得用户令牌调用 Auth3。

WebAdmin 和用户 Web 分别在登录前获取本端随机 CSRF 令牌。服务端通过独立的、前端可读的 CSRF Cookie 下发令牌，两端请求封装在写请求中通过专用请求头回传。按目标端隔离 Cookie，避免同浏览器并行登录时相互覆盖。服务端按目标端核对允许的请求来源，再校验请求头与 Cookie 中的令牌。普通业务写入、登录发起、浏览器回调页发起的换票请求、切租户与退出均在执行业务或消费登录事务前完成校验，失败返回 403。

同一环境各实例共享 Redis、键前缀和签名密钥。建议配置 `DATACLAW_ADMIN_SESSION_COOKIE_NAME`、`DATACLAW_WEB_SESSION_COOKIE_NAME`、`DATACLAW_SESSION_SECRET`、`DATACLAW_SESSION_REDIS_PREFIX`。两端 Cookie 名称须不同，密钥由部署环境独立生成，至少 32 个随机字节；示例文件只留占位。Cookie 沿用现有 Secure、SameSite 和 Domain 设置。

切租户成功时轮换会话 ID 并原子失效旧会话，退出时撤销当前端会话。并发中的旧请求不能回写或恢复失效记录。租约以 Auth3 验证结果为准，后台读取 Redis 不得延长用户登录有效期。固定令牌是否在剩余五分钟时刷新待单独确认。

### 后台管理资格探测

Auth3 的 `OpenApiAuthGuard` 在用户令牌跟随登录会话、开启滑动续期且带有 `jti` 时，会在鉴权授权通过后延长租约。这一行为覆盖 `GET /api/v3/me/full` 和 `GET /api/v3/app/roles`，即使请求携带 `x-auth3-passive: 1` 也会触发。资格查询使用机器凭证调用 `GET /api/v3/users/roles-permissions`，用户和租户取自已验证的请求身份。机器 Client 须获得 `user.roles_permissions` 接口和对应租户授权。该路径不提交用户令牌，真实环境的租约到期行为仍需联调验收。每次管理读写仍须依据当前角色绑定独立核验资格。

### 滑动会话守卫

认证中间件按请求用途决定是否续租（`renewActivity`），按会话模式独立决定是否允许自动刷新用户令牌（`allowRefresh`）。在 Auth3 滑动模式下，三端仅在用户交互触发对应的 `POST /api/v1/{admin,web,desktop}/auth/activity` 时续租。验票成功后复用活动处理器，使用当前用户令牌调用一次 Auth3 `/api/v3/me`。桌面端的 Bearer 活动请求适用同一规则。普通业务请求、后台轮询和恢复探测的认证流程只验票。

滑动模式下所有请求的 `allowRefresh` 均为 false，即使会话带有 `refresh_token`。Auth3 判定租约失效时沿用认证失败流程，要求重新登录。

### 浏览器会话与部署安全

两端的租户业务写请求携带页面加载时的租户 ID。服务端从已验证会话取得实际租户，在业务执行前拒绝预期租户缺失或不匹配的请求。切租户请求分别传递原租户和目标租户。同一会话跨实例串行切换，校验新令牌的用户、目标租户和 Client 后，按原登录批次原子轮换 SID。若派发后结果未知，标记待核实，阻止旧凭证继续写入或自动重试。

建立会话时记录固定截止时间；用户活动和租户切换均沿用该截止时间。Auth3 明确返回令牌失效时，只终止对应登录批次。网络或机器凭证故障时拒绝本次受保护操作并保留会话记录。本地退出和 SSO 回调分别记录结果；退出事务以随机一次性 state 绑定浏览器、端及原登录批次，五分钟内可原子消费一次。迟到回调只处理原事务。

两个 Web 部署入口按实际脚本、API、表单及资源来源生成并发送 Content-Security-Policy 响应头，以 frame-ancestors 'none' 禁止页面嵌入。联调覆盖登录导航、回调及主要业务页面。

### 管理写操作审计

对角色、权限码、角色权限绑定、成员变更、同步配置变更和手动同步，在业务副作用前持久化 PENDING 意图，记录请求标识、真实操作人、发起租户、动作和目标。写入意图失败即停止操作。按已确认结果更新成功或失败，业务结果未知或终态回写失败时保留待核实记录，禁止自动重放。手动同步审计关联执行记录，以逐租户执行历史追踪同步结果。审计查询按发起租户隔离并校验审计查看权限。

## Risks / Trade-offs

- Auth3 授权配置错误会影响多个入口。发布前分别验证三套回调、角色自管用户身份，以及机器 Client 的自省、目录、租户与消息接口授权。
- 组织 ID 的历史兼容性单独用现存记忆样本验证；异常时维持原访问边界。附件能力以真实交付结果验收。
- 同域 Cookie 或旧缓存可能串端；用同一浏览器同时登录管理端和用户端测试身份隔离。

## Migration Plan

先部署增量目录表和 Auth3 配置，登记管理端权限基线和初始管理员。联调环境验证三端登录、历史数据、AI 配额、角色成员、目录并发及通知，再协调切换服务与前端。回退时先停同步调度，再恢复配套的应用版本、认证配置与回调；保留同步数据及历史，用户重新登录。
