# admin-role-permissions Specification

## Purpose

使管理人员在管理端维护本应用的角色、权限码以及人员关联，并确保菜单显示、服务端授权和跨租户成员操作遵循同一套身份边界。

## Requirements

### Requirement: 管理本应用授权
系统 SHALL 在管理端提供权限矩阵、角色和权限码维护，通过 Auth3 应用管理员用户身份操作。

#### Scenario: 管理资格与入口
- **WHEN** 已验证的管理端用户持有本管理应用系统管理员角色 ID
- **THEN** 系统 SHALL 开放角色、权限码、角色权限绑定和当前租户角色成员的管理入口，并在每次管理读写时独立核验该资格

#### Scenario: 仅持有动作权限或其他应用角色
- **WHEN** 用户没有本应用系统管理员角色，但持有角色管理动作权限码或其他应用的同码角色
- **THEN** 管理端隐藏上述入口，直接访问对应页面或管理 API 也无法读取或更改授权数据

#### Scenario: 角色被撤销
- **WHEN** 用户已打开管理页面，随后其系统管理员角色被撤销
- **THEN** 服务端在下一次管理读写时拒绝该请求

#### Scenario: 独立业务权限
- **WHEN** 系统管理员缺少同步管理或审计查看权限
- **THEN** 对应业务入口和接口继续按各自权限码限制访问

#### Scenario: 授权变更
- **WHEN** 管理员创建角色、维护权限码并保存绑定
- **THEN** 刷新后读到 Auth3 中本应用的已保存结果

#### Scenario: 越权访问
- **WHEN** 普通用户直接请求管理 API 或请求修改其他应用角色
- **THEN** 服务端拒绝，目标授权数据保持原值

#### Scenario: 用户端导航
- **WHEN** 用户登录 dataclaw-web
- **THEN** 不显示角色权限及租户同步菜单，也不注册对应管理页面

### Requirement: 成员与有效权限
系统 SHALL 仅在用户令牌当前租户内维护本应用角色成员。

#### Scenario: 跨页选择
- **WHEN** 管理员跨页增删已获应用授权的成员
- **THEN** 只提交选择差量，其他成员关联保留

#### Scenario: 应用隔离
- **WHEN** 用户仅在其他应用具有同名权限码
- **THEN** 管理端按钮与后端守卫均不据此授予管理操作

### Requirement: 管理写操作前置审计
系统 SHALL 在角色、权限码、绑定或成员变更执行前持久化待执行意图，记录真实操作人和发起租户，按审计查看权限与发起租户限制查询。

#### Scenario: 审计存储不可用
- **WHEN** 意图写入失败
- **THEN** 拒绝管理操作，业务数据保持原值

#### Scenario: 执行结果回写
- **WHEN** 操作完成、明确失败或结果未知
- **THEN** 分别记录成功、失败或待核实，终态回写失败时保留原意图供核对，禁止自动重放


### Requirement: 按应用编码解析权限归属
系统 SHALL 使用 DATACLAW_WEBADMIN_APPLICATION_CODE 配置管理应用，在已验证用户的当前租户内解析唯一启用的 applicationId，并按该 ID 精确过滤用户权限。

#### Scenario: 权限归属解析
- **WHEN** 用户请求本应用权限
- **THEN** 服务端 SHALL 用机器凭证查询当前租户应用列表，按配置编码解析唯一启用的应用 ID，并仅采用该 ID 对应的权限项，解析结果按租户隔离

#### Scenario: 解析失败
- **WHEN** 应用缺失、重复、停用、返回字段无效或上游不可用
- **THEN** 系统 SHALL 返回 503 并拒绝受保护操作，不采用其他应用的同名权限

#### Scenario: 配置收敛
- **WHEN** 部署 Auth3 管理应用
- **THEN** 系统 SHALL 要求配置 DATACLAW_WEBADMIN_APPLICATION_CODE，移除 DATACLAW_WEBADMIN_APPLICATION_ID 和 AGENT_OS_APP_CODE，缺少新键不得通过旧键继续授权

### Requirement: 统一角色权限入口
系统 SHALL 在管理端系统配置分组提供唯一的“角色权限”菜单，地址为 `/role-permissions`，页面包含权限矩阵、角色管理、权限码管理三个 Tab，默认展示权限矩阵，并对所有 Tab 应用相同的现有管理资格限制。

#### Scenario: 进入统一页面
- **WHEN** 具备管理资格的用户点击角色权限菜单
- **THEN** 打开 `/role-permissions` 并展示权限矩阵，侧栏不再出现独立角色管理或权限码管理入口

#### Scenario: 旧地址兼容
- **WHEN** 用户访问 `/access-control`、`/roles` 或 `/permission-codes`
- **THEN** 分别重定向至 `/role-permissions` 的权限矩阵、角色管理或权限码管理 Tab，且不能绕过管理资格检查

#### Scenario: 切换与刷新
- **WHEN** 用户切换 Tab 或刷新带有 Tab 选择的页面地址
- **THEN** 展示对应 Tab，单次页面会话内切换保留各 Tab 搜索和分页状态，无效 Tab 值回到权限矩阵

### Requirement: 权限矩阵布局
系统 SHALL 以权限树为行、角色为列展示本应用完整权限矩阵，提供层级展开收起、滚动时固定表头与权限列，以及明确的绑定状态和角色关联维护入口。

#### Scenario: 查看矩阵与维护关联
- **WHEN** 管理员查看权限矩阵
- **THEN** 看到角色名称与编码、权限名称与编码、绑定状态图例，并可从角色表头打开权限配置或人员管理弹窗；矩阵状态单元格不直接修改绑定

#### Scenario: 不完整数据
- **WHEN** 角色目录或某角色绑定加载失败或不完整
- **THEN** 页面显示失败及重试入口，不将未知状态显示为未绑定，也不允许基于不完整数据覆盖保存

### Requirement: 角色与权限码维护布局
系统 SHALL 在角色管理和权限码管理 Tab 使用搜索工具栏、数据表格及编辑弹窗组织维护操作，搜索在左，刷新和新增操作在右，并适应窄屏布局。

#### Scenario: 管理角色
- **WHEN** 管理员打开角色管理 Tab
- **THEN** 展示可搜索分页表格，包含名称、编码、备注与操作列，提供新增角色、修改基本信息、配置权限、管理人员和删除操作

#### Scenario: 管理权限码
- **WHEN** 管理员打开权限码管理 Tab
- **THEN** 展示名称、编码、描述及操作的层级表格，支持新增根权限、添加子权限、修改和删除；搜索保留匹配节点的祖先路径

### Requirement: 编辑状态保护与反馈
系统 SHALL 在弹窗中明确区分基本信息、权限绑定和人员关联操作，并保护未保存输入，明确反馈加载、空数据、失败和保存结果。

#### Scenario: 离开草稿
- **WHEN** 用户在有未保存修改时关闭弹窗、切换 Tab 或离开页面
- **THEN** 提示用户确认放弃，取消后保留原编辑内容；保存进行中阻止重复提交及切换

#### Scenario: 保存与删除
- **WHEN** 用户保存编辑或确认删除
- **THEN** 成功后重新加载相关列表与矩阵，失败时保留可恢复输入且不宣称成功；删除需明确确认目标，人员跨页变更仍仅提交差量

#### Scenario: 资格失效与身份变化
- **WHEN** 管理资格被拒绝或用户、租户发生切换
- **THEN** 关闭编辑器并清理旧范围数据，迟到响应不能恢复旧数据或自动提交草稿

#### Scenario: 键盘操作
- **WHEN** 用户通过键盘切换 Tab 或打开关闭弹窗
- **THEN** Tab 选中状态与内容关联可被辅助技术识别，弹窗具有标题及焦点管理，关闭后焦点回到触发入口
